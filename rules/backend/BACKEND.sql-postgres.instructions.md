# Boas práticas de modelagem de banco de dados (PostgreSQL)

## 1) Comece pelo domínio e pelos casos de uso
- **Modele o negócio antes das tabelas**: entidades, relacionamentos, regras e eventos.
- Liste as **perguntas que o sistema precisa responder** (consultas mais comuns) e os **fluxos de escrita** (criações/atualizações).
- Defina claramente o que é **dado mestre** (cadastro) vs **transacional** (movimentação) vs **histórico/auditoria**.

## 2) Normalização como padrão (com desnormalização consciente)
- Use **3FN** como base (evita redundância e anomalias).
- Desnormalize **apenas** quando houver:
  - gargalo comprovado (medido),
  - impacto alto de JOINs repetidos,
  - e estratégia clara de manter consistência (triggers, jobs, view materializada, etc.).
- Prefira **views** (ou **materialized views**) para “modelos de leitura” quando fizer sentido.

## 3) Padrões de nomes e organização
- Use `snake_case` em tudo (tabelas, colunas, constraints).
- Tabelas no singular ou plural: escolha um padrão e **mantenha** (ex.: `customer` ou `customers`).
- Evite nomes reservados e genéricos: `user` (reservado em alguns contextos), `data`, `value`.
- Use schemas para separar áreas (ex.: `public`, `billing`, `iam`, `audit`) quando o projeto crescer.

## 4) Chaves primárias: escolha consistente
- **Padrão recomendado**: `bigint` identity (`GENERATED BY DEFAULT AS IDENTITY`) para PKs internas.
- Use **UUID** quando houver necessidade real: dados gerados offline, integração distribuída, segurança por não expor sequência, etc.
- Evite PK “inteligente” (ex.: CPF como PK). Use como **unique constraint**.

## 5) Integridade referencial e constraints (não deixe só para a aplicação)
- Sempre que possível, imponha no banco:
  - `NOT NULL` onde for obrigatório,
  - `CHECK` para regras simples (ex.: `price >= 0`),
  - `UNIQUE` para chaves naturais (ex.: `email`),
  - `FOREIGN KEY` para relacionamentos.
- Defina claramente `ON DELETE`/`ON UPDATE`:
  - `RESTRICT/NO ACTION` por padrão (mais seguro),
  - `CASCADE` só quando a regra for inequívoca,
  - `SET NULL` quando fizer sentido manter “órfão” válido.
- Use constraints com nomes explícitos: `customer_email_uniq`, `order_customer_id_fkey`.

## 6) Tipos de dados: use os tipos “certos” do PostgreSQL
- `numeric(p,s)` para dinheiro/valores exatos (ou `bigint` em centavos, se preferir).
- `timestamptz` para datas/hora (quase sempre melhor do que `timestamp`).
- `text` é ok; limite (`varchar(n)`) raramente traz ganho real.
- Use `boolean` de verdade (evite `0/1`).
- Use `jsonb` com moderação: ótimo para dados semi-estruturados, ruim como “substituto de modelagem relacional”.
- Considere `citext` (case-insensitive) para e-mails/logins, se fizer sentido.

## 7) Relacionamentos: N:N e tabelas de associação
- Relacionamento N:N deve virar **tabela de junção**:
  - PK composta (`(a_id, b_id)`) quando a junção não tiver identidade própria,
  - ou PK surrogate + `UNIQUE(a_id, b_id)` quando precisar de referência externa.
- Em tabelas de junção, crie índice para a direção de consulta mais comum (às vezes ambos).

## 8) Índices: crie para consultas reais, não por hábito
- Crie índices que suportem:
  - filtros (`WHERE`),
  - ordenação (`ORDER BY`),
  - joins (`FK` frequentemente precisa índice),
  - unicidade (`UNIQUE` já cria índice).
- Use **índices parciais** para dados “ativos” (ex.: `WHERE deleted_at IS NULL`).
- Use `GIN` para `jsonb` e busca textual (casos específicos).
- Regra de ouro: índice a mais melhora leitura e piora escrita; meça e ajuste.

## 9) Soft delete, auditoria e histórico
- Se usar soft delete, padronize: `deleted_at timestamptz` e, opcionalmente, `deleted_by`.
- Para auditoria, decida:
  - trilha simples (`created_at`, `updated_at`, `created_by`, `updated_by`),
  - ou tabelas de histórico (event sourcing/light audit),
  - ou extensão/ferramenta (dependendo do stack).
- Evite depender só de triggers sem documentação/testes: podem surpreender.

## 10) Migrações e evolução do esquema
- Toda mudança deve ser via **migração versionada** (Flyway, Liquibase, Prisma, Rails, Alembic etc.).
- Evite migrações destrutivas em produção:
  - prefira “expandir e contrair” (add coluna, popular, trocar uso, remover depois).
- Para grandes tabelas, cuidado com:
  - `ALTER TABLE` que reescreve tabela,
  - criação de índice sem `CONCURRENTLY` (quando aplicável).

## 11) Transações e concorrência (modelagem pensando em consistência)
- Modele pensando em transações curtas.
- Conheça e use:
  - `UNIQUE` para evitar duplicidade sob concorrência,
  - `SELECT ... FOR UPDATE` quando necessário,
  - `UPSERT` (`INSERT ... ON CONFLICT ...`) para idempotência.
- Seja explícito sobre o nível de isolamento quando o caso exigir (raro, mas importante).

## 12) Particionamento (quando realmente precisar)
- Considere particionar quando:
  - volume muito alto e tabelas “append-only” (logs, eventos, faturas),
  - necessidade clara de “data pruning” por período.
- Particionamento adiciona complexidade operacional: só adote com motivo e monitoramento.
